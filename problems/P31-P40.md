# Problems P31–P40

## P31 — Employee Data Sync (MERGE basic)
**Concept:** MERGE — update if exists, insert if new

```sql
MERGE #EmpTarget AS T
USING #EmpStaging AS S
ON T.EmpID = S.EmpID

WHEN MATCHED THEN
    UPDATE SET T.Department = S.Department,
               T.Salary     = S.Salary

WHEN NOT MATCHED BY TARGET THEN
    INSERT (EmpID, EmpName, Department, Salary)
    VALUES (S.EmpID, S.EmpName, S.Department, S.Salary);
```

**Key learnings:**
- TARGET = jo badlega (main table)
- SOURCE = jo compare karega (new data feed) — never modified
- Matching key = unique column (EmpID, not Name/Salary)
- Semicolon = sirf end mein, mandatory
- 90% real work = MATCHED (update) + NOT MATCHED BY TARGET (insert)

**MERGE skeleton — yaad karo:**
```
MERGE  Target          ← kahan jaana hai
USING  Source          ← kahan se aa raha hai
ON     T.ID = S.ID     ← kaise pehchano (matching key)
WHEN   ... THEN ...;   ← kya karo (semicolon end mein!)
```

## P32a — Product Inventory Sync (MERGE with DELETE)
**Concept:** All 3 WHEN cases — UPDATE + INSERT + DELETE

```sql
MERGE #ProductMain AS T
USING #ProductFeed AS S
ON T.ProductID = S.ProductID

WHEN MATCHED THEN
    UPDATE SET T.Stock = S.Stock

WHEN NOT MATCHED BY TARGET THEN
    INSERT (ProductID, ProductName, Stock)
    VALUES (S.ProductID, S.ProductName, S.Stock)

WHEN NOT MATCHED BY SOURCE THEN
    DELETE;
```

**Key learnings:**
- NOT MATCHED BY TARGET = "target mein nahi hai" → INSERT
- NOT MATCHED BY SOURCE = "source mein nahi hai" → DELETE or UPDATE
- NOT MATCHED BY TARGET = sirf INSERT allowed (row exist hi nahi, update kaise?)
- NOT MATCHED BY SOURCE = UPDATE/DELETE dono allowed (row target mein hai)

**3 cases cheat sheet:**
```
MATCHED             → dono mein hai        → UPDATE
NOT MATCHED BY TARGET → source mein, target nahi → INSERT
NOT MATCHED BY SOURCE → target mein, source nahi → DELETE/UPDATE
```

## P32b — Employee Sync with Audit Log (MERGE + OUTPUT)
**Concept:** OUTPUT clause — log every action

```sql
MERGE #EmpTarget AS T
USING #EmpStaging AS S
ON T.EmpID = S.EmpID

WHEN MATCHED THEN
    UPDATE SET T.Department = S.Department,
               T.Salary     = S.Salary

WHEN NOT MATCHED BY TARGET THEN
    INSERT (EmpID, EmpName, Department, Salary)
    VALUES (S.EmpID, S.EmpName, S.Department, S.Salary)

OUTPUT $action, inserted.EmpID, inserted.EmpName
INTO #MergeLog;
```

**Key learnings:**
- `$action` = automatically returns 'INSERT', 'UPDATE', or 'DELETE'
- `inserted.col` = new values (after change)
- `deleted.col` = old values (before change)
- OUTPUT goes before semicolon
- Real use: ETL audit logs, debugging, change tracking

## P32c — Customer ERP Sync (Production-level MERGE)
**Concept:** Soft delete + LastUpdated + OUTPUT log — real production pattern

```sql
MERGE #Customers AS T
USING #ERPFeed AS S
ON T.CustomerID = S.CustomerID

WHEN MATCHED THEN
    UPDATE SET T.City        = S.City,
               T.Salary      = S.Salary,
               T.LastUpdated = GETDATE()

WHEN NOT MATCHED BY TARGET THEN
    INSERT (CustomerID, CustomerName, City, Salary, IsActive, LastUpdated)
    VALUES (S.CustomerID, S.CustomerName, S.City, S.Salary, 1, GETDATE())

WHEN NOT MATCHED BY SOURCE THEN
    UPDATE SET T.IsActive = 0

OUTPUT $action, inserted.CustomerID, inserted.CustomerName
INTO #SyncLog;
```

**Key learnings:**
- Soft delete = IsActive = 0, never real DELETE in production
- LastUpdated = GETDATE() = audit trail on every update
- NOT MATCHED BY SOURCE mein bhi UPDATE ho sakta hai (DELETE mandatory nahi)
- OUTPUT captures all 3 action types automatically

**Pattern name: Production ETL Sync**
> Real use: nightly ERP sync, CRM data refresh, master data management

## MERGE Performance Warning

```
MERGE has documented race condition issues on high concurrency.
SQL Server 2008-2019 mein officially acknowledged bug.

USE MERGE:    batch jobs, nightly ETL, low concurrency, small-medium tables
AVOID MERGE:  high concurrency, billion-row tables, mission-critical real-time

Production-safe alternative:
  UPDATE with INNER JOIN  → update existing
  INSERT with NOT EXISTS  → insert new
  Separate statements = better locks, better plans
```

**Interview answer:**
> "MERGE is convenient but has documented race condition issues on high concurrency.
>  For production ETL on large tables I prefer separate UPDATE + INSERT with EXISTS check."
