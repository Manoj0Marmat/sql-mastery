# Problems P24–P30

## P24 — Running Department Budget
**Concept:** Running total + percentage of total

```sql
WITH CTE AS (
    SELECT EmpName, Salary,
        SUM(Salary) OVER (PARTITION BY Department
                          ORDER BY Salary DESC
                          ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS RunningTotal,
        SUM(Salary) OVER (PARTITION BY Department) AS DeptSalary
    FROM Employees
)
SELECT EmpName, Salary, RunningTotal,
    CAST((RunningTotal * 100.0) / DeptSalary AS DECIMAL(10,2)) AS PctOfDept
FROM CTE
ORDER BY Department, Salary DESC
```

**Key learnings:**
- `SUM() OVER (ORDER BY ... ROWS BETWEEN ...)` = running total
- `SUM() OVER (PARTITION BY dept)` no ORDER BY = whole partition same value
- `* 100.0` not `* 100` — INT * INT = INT, truncates decimal

## P25 — Salary Spike Detection
**Concept:** LAG for period-over-period comparison, threshold filter

```sql
WITH CTE AS (
    SELECT EmpName, EffectiveDate, Salary AS NewSalary,
        LAG(Salary) OVER (PARTITION BY EmpID ORDER BY EffectiveDate) AS PrevSalary
    FROM SalaryHistory
)
SELECT EmpName, PrevSalary, NewSalary,
    CAST((NewSalary - PrevSalary) * 100.0 / PrevSalary AS DECIMAL(10,2)) AS PctIncrease,
    EffectiveDate
FROM CTE
WHERE PrevSalary IS NOT NULL
  AND (NewSalary - PrevSalary) * 100.0 / PrevSalary > 20
ORDER BY EmpName, EffectiveDate
```

**Key learnings:**
- LAG not LEAD — "previous salary" = look backward
- ORDER BY EffectiveDate (date) not Salary (value) — chronological order
- WHERE PrevSalary IS NOT NULL — first row per employee has no previous
- Growth formula: `(Current - Previous) * 100.0 / Previous`

**Pattern name: Period-over-Period Comparison**
> LAG + percentage + threshold filter
> Real use: salary spikes, MoM revenue change, stock alerts, SLA breach detection

**Common mistake fixed:**
```sql
-- WRONG: orders by salary value (breaks if salary decreases)
LAG(Salary) OVER (PARTITION BY EmpID ORDER BY Salary)

-- CORRECT: orders by date (always chronological)
LAG(Salary) OVER (PARTITION BY EmpID ORDER BY EffectiveDate)
```

## P26 — First and Last Transaction
**Concept:** FIRST_VALUE + LAST_VALUE with correct frame

```sql
SELECT DISTINCT
    CustomerName,
    FIRST_VALUE(OrderDate) OVER (PARTITION BY CustomerID ORDER BY OrderDate) AS FirstOrder,
    LAST_VALUE(OrderDate)  OVER (PARTITION BY CustomerID ORDER BY OrderDate
                                 ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS LastOrder,
    FIRST_VALUE(Amount)    OVER (PARTITION BY CustomerID ORDER BY OrderDate) AS FirstAmount,
    LAST_VALUE(Amount)     OVER (PARTITION BY CustomerID ORDER BY OrderDate
                                 ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS LastAmount
FROM Orders
```

**Key learnings:**
- FIRST_VALUE → no frame needed, always correct
- LAST_VALUE → ALWAYS add full frame or it returns current row's value
- DISTINCT collapses duplicate rows per customer

**LAST_VALUE frame trap:**
```
Default frame = UNBOUNDED PRECEDING to CURRENT ROW
→ "last so far" changes every row

Fix: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
→ "last in entire partition" same on every row
```

**Pattern name: First and Last per Group**
> Real use: first/last login, first/last transaction, first/last status change

## P27 — Monthly Sales Growth
**Concept:** LAG for MoM growth, keep NULL on first row

```sql
WITH CTE AS (
    SELECT SaleYear, SaleMonth, Revenue,
        LAG(Revenue) OVER (ORDER BY SaleYear, SaleMonth) AS PrevRevenue
    FROM MonthlySales
)
SELECT SaleYear, SaleMonth, Revenue, PrevRevenue,
    CAST((Revenue - PrevRevenue) * 100.0 / PrevRevenue AS DECIMAL(10,2)) AS GrowthPct
FROM CTE
```

**Key learnings:**
- ORDER BY SaleYear, SaleMonth — Year first, then Month (not Month first!)
- Keep NULL on first row — don't filter it, it's correct (no previous month)
- INT / INT = INT → always use `* 100.0` to force decimal

**Bug pattern:**
```sql
-- WRONG order — breaks across multiple years
LAG(Revenue) OVER (ORDER BY SaleMonth, SaleYear)

-- CORRECT — always chronological
LAG(Revenue) OVER (ORDER BY SaleYear, SaleMonth)
```

## P28 — Top 3 Products Per Category
**Concept:** RANK/DENSE_RANK per group, filter top N

```sql
WITH CTE AS (
    SELECT Category, ProductName, Revenue,
        RANK() OVER (PARTITION BY Category ORDER BY Revenue DESC) AS Rank
    FROM ProductSales
)
SELECT Category, Rank, ProductName, Revenue
FROM CTE
WHERE Rank <= 3
ORDER BY Category, Rank
```

**Key learnings:**
- RANK safer than DENSE_RANK for "top N" with ties
- DENSE_RANK tie example: if two products tied at rank 2, DENSE_RANK gives rank 3 to next → 4 rows for "top 3"
- RANK tie example: next product gets rank 4 → still only 3 rows for WHERE Rank <= 3

**RANK vs DENSE_RANK for top N:**
```
Tie at rank 2:
RANK        → 1, 2, 2, 4   WHERE <= 3 = 3 rows  (correct)
DENSE_RANK  → 1, 2, 2, 3   WHERE <= 3 = 4 rows  (extra row!)
```

## P29 — Customer Loyalty Tier
**Concept:** NTILE for bucket classification

```sql
SELECT CustomerName, TotalSpend,
    CASE NTILE(4) OVER (ORDER BY TotalSpend DESC)
        WHEN 1 THEN 'Platinum'
        WHEN 2 THEN 'Gold'
        WHEN 3 THEN 'Silver'
        ELSE        'Bronze'
    END AS Tier
FROM CustomerSpend
ORDER BY TotalSpend DESC
```

**Key learnings:**
- NTILE(4) splits into 4 equal groups automatically
- ORDER BY DESC → group 1 = top earners
- Uneven rows → top groups get extra row first (10 rows, 4 groups = 3,3,2,2)
- CASE directly on NTILE result — no CTE needed

**NTILE cheat sheet:**
```
NTILE(4)   → quartiles  (top 25%, 25-50%, 50-75%, bottom 25%)
NTILE(10)  → deciles    (top 10%, bottom 10%)
NTILE(100) → percentiles
```

**Pattern name: Bucket Classification**
> Real use: loyalty tiers, risk scoring, sales rep ranking, student grades

## P30 — Employee Performance Summary (Synthesis)
**Concept:** All window functions combined — COUNT, AVG, DENSE_RANK, CASE

```sql
WITH CTE AS (
    SELECT Department, EmpName, Salary,
        COUNT(1)                   OVER (PARTITION BY Department) AS HeadCount,
        AVG(CAST(Salary AS DECIMAL(10,2))) OVER (PARTITION BY Department) AS AvgSalary,
        DENSE_RANK()               OVER (PARTITION BY Department ORDER BY Salary DESC) AS Rank
    FROM Employees
)
SELECT Department, EmpName, Salary, HeadCount, AvgSalary, Rank,
    CASE
        WHEN Salary > AvgSalary THEN 'Above'
        ELSE 'Below'
    END AS VsAvg
FROM CTE
ORDER BY Department, Rank
```

**Key learnings:**
- All window functions in one CTE — single table scan
- COUNT, AVG, DENSE_RANK all use same PARTITION BY — optimizer shares the sort
- CASE in outer SELECT references CTE columns directly — clean and readable
- No JOIN needed — everything computed in one pass

**Why this is production-grade:**
```
Single scan    → no repeated reads
Single CTE     → no temp tables
Window sharing → optimizer reuses sort for all three functions
```

**P30 = synthesis of:**
```
P1–P7   GROUP BY aggregates        → replaced by window functions here
P12–P13 DENSE_RANK                 → rank per department
P9      CTE pattern                → single CTE approach
P10     Cross-partition comparison → salary vs dept avg
```
